# 開発メモ

## 2026-11-03 案を2つ反映すると、材料の遅れが二重に入る

1. **何を作ろうとしたか**：Claude が出した組み替え案を、担当者がボタン1つで計画に反映できるようにする
2. **Claude にどう指示したか**：Claude Code に「壁打ちした内容を全部対応して」と頼み、案のカードには「変更の組み合わせ」を持たせる形で作ってもらった
3. **何が起きたか**：Claude Code が自分でブラウザを操作して確かめたところ、どの案にも「材料が2日遅れる」という出来事そのものが含まれていた。2つの案を続けて反映すると、遅れが4日になる
4. **期待とどう違ったか**：案は「出来事への対策」であってほしかったが、出来事と対策が1つの変更リストに混ざっていた
5. **どう対処したか**：Claude に渡すツール `present_options` を、出来事（`event`）と対策（各案の `changes`）に分ける形に変えた。反映するときは、まだ計画に入っていない出来事だけを足す。1つの提案の中で1つの案を反映したら、ほかの案は閉じる。カードには「何もしないと」の影響も出すようにした

## 2026-11-03 方針の見直し：計画・スケジュール・評価の3段にする

1. **何を作ろうとしたか**：本物の Claude で「材料が2日遅れる」の相談が通り、案が3つ出るところまでできた
2. **Claude にどう指示したか**：動きを見た計画担当の目線で、「これだと対象の型番の予定をずらしているだけに見える。今月必ず出すもの（在庫切れ）と来月切れるものから計画を立て、その通りに進めれば納期を守れるか、当月の採算はどうなるかまで出したい」と伝え、Claude Code と相談役のモデルの両方とすり合わせた
3. **何が起きたか**：スケジューラは試算のたびに全注番を全設備で組み直しており、整合は取れていた。足りないのは入力と評価だった。在庫と消費から出す需要の段、優先の区分、形状から形状への段取り時間、出勤人数、お金がなかった
4. **期待とどう違ったか**：「出来事に対して予定がどう動くか」は出せても、「この計画で今月を乗り切れるか、いくら残るか」には答えられなかった
5. **どう対処したか**：残りの日数に合わせて順番を決めた。先に、需要と優先の区分（A 今月必達／B 来月在庫切れ／C 余力）、形状の段取り表、粗利（当月完成分の売上 − 材料費 − 労務費（残業25%・休日35%増し）− 設備の時間費）を入れる。次に、工程のまとまりごとの日別の出勤人数を入れる。最適化の計算、設備ごとのサイクルタイム、Lot の分割は見送る

## 2026-11-03 人を日単位で設備に付けたら、1人の班で引き継ぎに1日空いた

1. **何を作ろうとしたか**：班（工程のまとまり）ごとの日別の出勤人数を入れ、設備1台に1人として、同時に動く設備の数を絞る
2. **Claude にどう指示したか**：Claude Code に、出勤人数の設計を相談役のモデルとすり合わせてから実装するよう頼んだ。最初の案は「その日に働いた設備に、その班の人を1日つける」だった
3. **何が起きたか**：テストは通ったが、サンプルで機械班を1人にして試算すると、注番1045が切削を終えたあと、熱処理が翌日まで始まらなかった。切削の設備にその日の1人がついたままになっていた
4. **期待とどう違ったか**：現場では、切削が終われば同じ人が熱処理に移る。日単位の割り当てでは、人が足りない班ほど、工程の引き継ぎごとに半日〜1日が無駄に空く
5. **どう対処したか**：「その時刻に同時に動いている班の設備の数 ≦ その日の人数」を、稼働時間の区切りごとに数える方式に変えた。空かないときは、ほかの設備の作業が終わる時刻まで待つ。同じ班の人を取り合うときは、区分（A → B → C）の高い作業に人を回す。人が同じ日に別の設備へ移れることをテストに足した

## 2026-11-04 ガントから進捗へ移ったあと、検索を戻すとフォーカスを奪われた

1. **何を作ろうとしたか**：ガントのバーから「進捗で見る」を押すと、進捗タブでその Lot の行が強調され、キーボードのフォーカスもその行に移るようにする
2. **Claude にどう指示したか**：Claude Code に、ガントと進捗に足りないところを洗い出して、締切までにやるものは全部対応するよう頼んだ。夜のうちに実装し、検証役のサブエージェントに、決めた観点で実際に操作して確かめてもらう流れにした
3. **何が起きたか**：テストと見た目の確認は通った。検証役が、移ったあと検索欄に入力して行を消し、検索を戻すと、Lot の一覧が開き直り、入力中のフォーカスが Lot の行へ移ることを見つけた。強調した行の中のリンクも、ライト表示で文字と背景の対比が 4.33:1 しかなかった
4. **期待とどう違ったか**：フォーカスを移すのは、移ってきた最初の一度だけのつもりだった。実際は、一覧が表示し直されるたびに移していて、入力の途中で操作の場所が変わる（WCAG 3.2.2）
5. **どう対処したか**：絞り込みで行が消えたら一覧を閉じ、検索を戻しても勝手に開き直さないようにした。Lot の行へのフォーカスは、タブを開いた最初の一度だけにして、強調の表示は残した。閉じたとき開いた元のボタンがなければ、検索欄へ戻す。選んだ行の塗りは薄くして左端の線で示し、行の中の文字はどれも 4.5:1 以上にした。検証は3回まで回し、3回目で提出してよい水準と判定してもらった

## 2026-11-04 速い設備を入れたら、設備を止めたほうが計画がよくなった

1. **何を作ろうとしたか**：1台で複数の工程を受け持つ複合機と、同じ工程でも設備ごとに違う速さを入れ、企業ごとの設備の違いを Excel で書けるようにする
2. **Claude にどう指示したか**：Claude Code に、複合機と設備ごとの速さを締切までに入れるよう頼んだ。サンプルは、マシニング1を複合機に、溶接ロボ2を速い設備にした。サンプルを変えるとデモの数字が動くので、変える前の数字を控え、デモで使う場面（材料の遅れ、数量の変更、設備の停止）を前後で比べるよう進めた
3. **何が起きたか**：テストは通ったが、比べると、「溶接ロボ1が明日1日止まる」場面で、粗利が上がり、注番1021が早く終わった。原因は2つあった。1つは、変える前からの癖で、スケジューラが長い作業の前で、あとから来る急ぎの作業を待って、溶接ロボ1を丸1日空けていた。もう1つは速さで、スケジューラは早く終わる設備を選び、安く済む設備は選ばない。遅い溶接ロボ1を止めると、仕事が速い溶接ロボ2に回り、人と運転費が減って粗利が上がった
4. **期待とどう違ったか**：設備が止まれば、計画は同じか悪くなるはず。デモで Claude が「止まると粗利が上がる」と話せば、計画そのものが信用されない
5. **どう対処したか**：急ぎの作業を待ってよい幅を、いちばん早く始められる時刻から、いちばん早く終われる時刻までの 3/4 に絞り、長い作業の前で設備を何時間も空けないことをテストに足した。サンプルの速さは、代わりの設備がないベンダー1に移した。複合機の2つ目の工程も、ボール盤と取り合わない「タップ」にした（取り合うと、材料が遅れたときに穴あけが安いボール盤へ回り、粗利が増えて見えた）。検証役が、作った日がずれた保存データや土日でも試し、溶接ロボ2が速いままだと、止めて粗利が上がる組み合わせが増えることを見つけた。そこで、24日 × 作った日のずれ3通り × 10台の停止で、変える前のコードと数え比べた。止めて粗利が上がる組み合わせは、変える前もあとも、11/19 以降（月末近く）に開いたときだけ出る。止めると仕事が来月へ移り、今月の売上は変わらないまま、今月の労務費と運転費だけが減るからで、今月の粗利という数え方から来る。止めて完成が早まる組み合わせは、変える前の39件が36件になり、平日に止めて早まるものはなくなった。新しく開いたサンプルでは、11/4〜11/10 のどの日も、材料の遅れで必ず遅れが出て、平日に開いて次の稼働日に溶接ロボ1を止めると、どの注番も完成が同じか遅くなり、早まるものはない。土日に開くと、1021 が遅れて 1022 が早まる入れ替わりが出る（変える前と同じ）。決まった手順で組むスケジューラなので、こうした入れ替わりは、最適化を入れない限り残る

## 2026-11-04 判断を取り消したら、画面が真っ白になる道ができていた

1. **何を作ろうとしたか**：足りない分の材料の発注期限と、代理店の在庫から注文が来る見込みを出す。Claude が、材料の入荷を待たせる案を組めるようにする
2. **Claude にどう指示したか**：Claude Code に実装を頼み、アプリの Claude の役を演じるサブエージェントに相談させた。そこで「足した注番を後回しにする書き方が分からない」と言われたので、ツールの説明に「足した注番には追加1、追加2…と番号が付き、hold で指定できる」と書き足した
3. **何が起きたか**：検証役が、その番号は採用済みの判断を前から当て直すたびに振り直されることを見つけた。判断1で注番を足し、判断2で足した注番を後回しにしてから判断1を取り消すと、後回しの相手がなくなる。計画を組むところでエラーになり、画面全体が真っ白になる。番号が詰まって、別の注番を後回しにしてしまう場合もあった
4. **期待とどう違ったか**：番号は、足したときに決まって変わらないものだと思っていた。説明を足したことで、Claude がその番号を使う案を出しやすくなり、壊れる道が近くなった
5. **どう対処したか**：採用するときに、足した注番の番号を判断の中に書き込んで固定した。取り消すと後の判断が新しく当てられなくなるときだけ、取り消さずに、どの判断が使っているかを出す。それでも当てられない変更が残っている保存データでは、その変更だけを外して計画し、画面の上に知らせる。Claude が出した案が、あとで当てられなくなっていたら、表示を閉じて理由を出し、反映もしない。テストに、取り消したあとも番号が変わらないことと、当てられない変更で計画が止まらないことを足した
